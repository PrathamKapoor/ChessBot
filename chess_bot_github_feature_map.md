# Pocket AI Chess Bot: GitHub Feature Map

Research snapshot: 2026-10-02. This is a representative, source-checked map of public repositories found through GitHub search and project links, not a claim that every chess repository on GitHub has been enumerated. Features below are those described in project documentation/source. Repository Elo statements are not treated as comparable unless independently measured under the same test conditions.

## Repository map

| Repository | Kind | Features documented | What Pocket AI can learn from it |
|---|---|---|---|
| [official-stockfish/Stockfish](https://github.com/official-stockfish/Stockfish) | Production UCI engine; strongest practical baseline | C++ engine; UCI; NNUE evaluation; optimized alpha-beta search; multithreading; configurable hash, threads, pondering, MultiPV and strength controls; Fishtest testing infrastructure; NNUE nets separated/documented in the networks repo. GPL-3.0. | Use as the strength and move-legality baseline. Its advantage comes from search, implementation speed, NNUE and huge-scale testing together, not a large general-purpose network alone. Audit GPL obligations before integrating or distributing derivatives. |
| [LeelaChessZero/lc0](https://github.com/LeelaChessZero/lc0) | Neural-search engine | UCI; policy/value neural nets; MCTS/self-play ecosystem; backends for CPU CBLAS, CUDA/cuDNN, ROCm/HIP, ONNX Runtime, Apple Metal, and experimental SYCL. ## Feature inventory across these repositories

| Feature area | Existing patterns found | Relevance to a lightweight competitive bot |
|---|---|---|
| Board/rules | FEN/UCI positions, legal move generation, castling/en-passant/promotions, check/mate/stalemate, repetition and 50-move draws | Correctness is a prerequisite. Start with a trusted rules library or a well-tested native move generator. A bot that mis-handles game state loses regardless of model size. |
| Search | Negamax/minimax, alpha-beta, iterative deepening, quiescence, PVS, aspiration windows, null move, LMR, futility/razoring, SEE, singular extensions | High priority for strength per compute. Search tactical continuations; don't expect a larger evaluator to replace lookahead. Add advanced pruning only with match testing. |
| Evaluation | Material/PST/phase-aware handcrafted eval; NNUE/HalfKP; DNN; policy/value networks | For CPU inference, NNUE is a particularly relevant compact evaluation approach because piece changes can update the accumulator incrementally. A general language foundation model is not a chess evaluator. |
| Move ordering and memory | Transposition tables with Zobrist keys; history/killer/countermove; capture ordering; cached neural results | Often converts hardware budget into deeper search. Measure nodes/sec, effective depth, and playing strength, not parameter count alone. |
| Parallelism/runtime | Lazy SMP; Cython/C++ hot paths; quantized int8/int16 NNUE; ONNX Runtime; CPU/GPU-specific neural backends | Optimize for target deployment hardware. CPU-friendly quantized NNUE and native search are a sensible first design for “lightweight.” |
| Training | NNUE supervised/score learning; self-play; AlphaZero policy/value updates; human-game move prediction; data generation/dedup and validation | Pick the training target based on intended play style. Human move prediction is not the same objective as winning; self-play produces stronger play but costs more compute and evaluation discipline. |
| Opening/endgame knowledge | Polyglot books, online books, Syzygy/Gaviota tablebases | Small storage can add reliable opening variety and exact endgame play. Tablebases help only in supported endgames and need storage/probing support. |
| Difficulty/personality | Skill/Elo limiting, randomized weighted move selection, Maia rating models, time allocation controls | A strong engine can expose a weaker mode without weakening the core. Randomize among acceptable candidates carefully; random blunders can make play look artificial. |
| Interfaces/testing | UCI; GUI; online bot adapter; match runners; Fishtest/OpenBench; benchmark/eval scripts | UCI first gives easy access to GUIs and reproducible matches. Establish a fixed baseline and test at equal time/nodes before adding features. |

## Early improvement hypotheses for Pocket AI

1. **Do not begin with a high-parameter Hugging Face foundation model.** Chess engines win through exact legality, efficient search, chess-specific evaluation and testing. A text-generation model's pretrained representations and objective do not directly provide those features.
2. **Use a hybrid architecture as the first serious target:** compact NNUE (or learned evaluation) plus alpha-beta search, iterative deepening, quiescence, transposition table and strong move ordering. Keep a classical evaluator as a fallback/debugging baseline.
3. **Separate engine from product shell:** engine speaks UCI; local GUI/web UI and any authorized platform connector live outside the search core.
4. **Build a test ladder:** perft/rule tests; tactical puzzle suite; fixed-node or fixed-time engine matches; opening diversity; endgame/tablebase checks; then user-facing bot matches. Compare against Stockfish at controlled resource limits and record win/draw/loss, not isolated self-reported Elo.
5. **Model a human-like difficulty mode separately:** Maia-like human move probabilities can provide style and rating calibration. Keep “best move” mode distinct from “human-like” mode.

## Scope and cautions

- GitHub search cannot prove the list is exhaustive; this first map prioritizes active, documented projects and distinct approaches (NNUE + alpha-beta, AlphaZero/MCTS, human imitation, minimal engine, and bot integration).
- Chess.com opponent bots are not open-source GitHub engines. This pass maps public repositories, not their internal implementation. They can be treated as external play-test opponents where platform rules permit.
- A repository's claimed Elo varies with hardware, time control, opponent pool, openings, and version. Do not compare claims across these READMEs as if they shared a rating test.
- Check each repository's license before copying code, weights, or datasets. GPL/AGPL obligations differ from MIT and from dataset/model terms.
